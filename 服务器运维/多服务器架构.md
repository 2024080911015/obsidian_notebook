# 多服务器架构

## 一、概述

多台服务器协同运行一个网站是现代 Web 架构的标准实践。核心思想是将不同的任务和负载分配到不同的服务器上，通过协同工作提供高效、可靠的 Web 服务。

### 典型架构组成

```
用户请求
   ↓
负载均衡 (Load Balancing)
   ↓
Web 服务器集群 (Web Server Cluster)
   ↓
文件存储同步 (File Storage & Sync)
   ↓
数据库集群 (Database Cluster)
   ↓
会话管理 (Session Management)
```

## 二、负载均衡

负载均衡器是流量的统一入口和智能分发中心。

### 1. DNS 轮询

**原理**：在 DNS 服务器上为同一域名配置多个 A 记录，分别指向不同的 Web 服务器 IP。

- **优点**：配置简单，成本低
- **缺点**：健康检查能力弱，某台服务器宕机时 DNS 缓存过期前仍可能返回失效 IP；负载分配不均衡

### 2. 软件负载均衡（Nginx/HAProxy/LVS）

Nginx 是最主流的方案之一，具备七层（HTTP）和四层（TCP）负载均衡能力。

**Nginx 负载均衡配置示例：**

```nginx
http {
    # 定义后端服务器集群
    upstream my_website {
        # 可选：ip_hash 确保同一客户端始终路由到同一台服务器
        # ip_hash;

        server 192.168.1.11;  # Web服务器1
        server 192.168.1.12;  # Web服务器2
        server 192.168.1.13; # Web服务器3
    }

    server {
        listen 80;

        location / {
            # 将所有请求转发到后端服务器集群
            proxy_pass http://my_website;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        }
    }
}
```

- **优点**：功能强大，健康检查，策略灵活，是目前最主流的方案
- **缺点**：需专用服务器，有一定配置和维护成本

^nginx-load-balance

### 3. 常用负载均衡策略

- **轮询（Round Robin）**：按顺序依次分发，默认方式
- **最少连接数（Least Connections）**：发给当前连接最少的服务器
- **IP 哈希（ip_hash）**：同一 IP 的请求始终发到同一台服务器（用于 Session 保持）

## 三、Web 服务器集群

负载均衡器之后是处理用户请求的 Web 服务器集群。

### 集群特点

- 每台服务器拥有**相同的网站代码和配置**
- 无论负载均衡器将请求发给哪台服务器，用户得到的响应一致
- 负责处理动态请求（PHP、Java、Python 等）和静态资源（图片、CSS、JS）

### 代码部署

可通过 [[宝塔面板部署]] 或手动方式在每台 Web 服务器上部署相同的应用代码。

## 四、文件存储与同步

当网站代码更新或用户上传文件时，必须确保所有 Web 服务器的文件一致。

### 1. rsync 定时同步

```bash
# 在主服务器上配置 crontab
# 每 5 分钟将 /var/www/html/ 同步到两台从服务器

*/5 * * * * /usr/bin/rsync -az --delete /var/www/html/ user@192.168.1.12:/var/www/html/
*/5 * * * * /usr/bin/rsync -az --delete /var/www/html/ user@192.168.1.13:/var/www/html/
```

- **优点**：配置简单，资源消耗低
- **缺点**：存在同步延迟（最多 5 分钟），不适合实时性要求高的场景

### 2. 共享存储（NFS/SAN）

将所有 Web 服务器通过网络挂载同一个共享存储目录，实时读写同一份文件。

- **优点**：实时一致，无同步延迟
- **缺点**：共享存储设备可能成为单点故障和性能瓶颈

### 3. 分布式文件系统（GlusterFS / Ceph）

将多台服务器的存储聚合为统一的虚拟文件系统，数据自动同步和冗余。

- **优点**：高可用，可扩展，无单点故障
- **缺点**：架构复杂，运维要求高

^file-sync-options

## 五、数据库集群

### 1. 主从复制（Master-Slave Replication）

最经典的数据库分布式方案：

- **主库（Master）**：负责所有写操作
- **从库（Slave）**：实时同步主库数据，负责读操作

架构优势：
- 实现**读写分离**，提升读取性能
- 成熟稳定，几乎所有数据库都支持

缺点：主库宕机时需手动将从库提升为新主库，有短暂服务中断和数据丢失风险。

### 2. 数据库集群（MySQL Cluster / Galera Cluster）

多台数据库服务器组成集群，所有节点都可读写，数据强同步。

代表方案：Percona XtraDB Cluster、Galera Cluster for MySQL。

- **优点**：高可用，无单点故障，一个节点宕机集群仍正常服务
- **缺点**：架构复杂，对网络要求高，写入性能可能有轻微下降

^db-cluster

## 六、分布式会话管理（Session）

多台 Web 服务器之间共享用户登录状态。

### 1. Session 粘性（Sticky Sessions）

在负载均衡器配置 `ip_hash`，确保同一用户的所有请求都转发到同一台服务器。

- **优点**：实现简单
- **缺点**：如果目标服务器宕机，Session 丢失。负载可能不均衡。

### 2. Session 共享（推荐）

将所有用户的 Session 数据集中存储到可共享的存储中。

**常用方案：**

- **Redis**：将 Session 存入 Redis 内存数据库，读写极快（最流行方案）
- **Memcached**：类似 Redis，也是内存缓存
- **MySQL**：将 Session 存入数据库（可能影响性能）

Redis Session 共享配置示例（以 Laravel 为例）：

```php
// config/session.php
'driver' => 'redis',
'connection' => 'session',
```

所有 Web 服务器连接到同一个 Redis 实例，读取和写入 Session 都走 Redis，确保用户在任何一台 Web 服务器上都能被正确识别。

^session-sharing

## 七、推荐架构方案

### 入门级架构

```
Nginx (负载均衡)
    ↓
多台 Web 服务器 (rsync 同步)
    ↓
MySQL 主从复制
    ↓
Redis (Session 共享)
```

### 高可用架构

```
HAProxy/Nginx 高可用集群
    ↓
Web 服务器集群 (NFS 或分布式文件系统)
    ↓
MySQL 集群 (Galera/Percona XtraDB)
    ↓
Redis 集群 (Session 共享)
```

搭建多服务器架构需根据业务需求、预算和技术储备选择合适方案。建议从简单的负载均衡 + 数据库主从复制开始，随业务增长逐步演进。

^architecture-recommendations
